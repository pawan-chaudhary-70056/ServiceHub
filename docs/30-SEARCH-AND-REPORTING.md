# 30 — Search and Reporting

**Status:** Approved · **Owner:** Backend Lead · **Reviewer:** Product Lead · **Approved:** 2026-10-01
**Consolidates:** old 63, 64

> **Scope:** the read model — cross-entity search, filtering/sorting conventions, and
> analytical reporting. **The query and index strategy** that makes this fast is `09`
> and `33`; **the per-endpoint parameters** are listed in `11`.

---

## 1. Purpose

Search and reporting are the same engineering concern seen at two time horizons:
search serves "find this now", reporting serves "what happened over time". Both fail
for the same reason — **a query that reads rows the caller may not see, or that scales
with the size of the table instead of the size of the result.** Every rule here exists
to prevent one of those two failures.

## 2. Search

### 2.1 Scope and sources

| Source | Owner | Indexed fields | Ranking weight |
|---|---|---|---|
| Service requests | `22` | `reference`, `title`, `description` | `reference` highest |
| Incidents | `23` | `reference`, `title`, `description`, `resolutionSummary` | `reference` highest |
| Tasks | `24` | `title` | — |
| Knowledge articles | `27` | `title`, `summary`, `body` | `title` > `summary` > `body` |
| Catalog items | `21` | `name`, `description` | `name` > `description` |
| Assets | `28` | `tag`, `serialNumber`, `name` | `tag`/`serial` exact-first |
| Users | `06` | `displayName`, `email` | exact-first |

### 2.2 Technology decision

**Default: PostgreSQL full-text search (`tsvector` + `tsquery` + GIN index).**

Rationale: one datastore, transactional consistency with writes, no second system to
operate, and no sync pipeline to get wrong. An external index (Elasticsearch,
OpenSearch) is considered only when a measured requirement — sub-100 ms fuzzy search
over millions of documents with typo tolerance — cannot be met. That is an ADR, not a
default (`42`).

The `08` §7 open question on this is resolved by this document **in favour of
PostgreSQL FTS for v1**; the external-index threshold is stated in §2.6.

### 2.3 The two rules that matter most

| # | Rule | Reason |
|---|---|---|
| S1 | **Visibility is a SQL predicate, applied before ranking and before pagination.** | Filtering search results in the application after querying means the ranking, the counts, and the page sizes are all computed over rows the caller cannot see — the canonical search authorization leak |
| S2 | **Never rank, then filter, then paginate.** The order is filter → rank → paginate, expressed as one query. | Post-filtering produces short pages, wrong totals, and timing channels |

These two rules are the security core of search (`17`). A defect here is an IDOR-class
issue that reviewers systematically miss because the code "looks like a search".

### 2.4 Query behaviour

| Concern | Behaviour |
|---|---|
| Query too short | <2 characters → no FTS; exact reference/tag match only |
| No results | Fall back to prefix matching, then to exact identifiers; the UI states the fallback used |
| Typos | Not supported in v1 (PostgreSQL FTS has no fuzzy match); stated as a known limitation |
| Sorting | Relevance for text queries; field sort when a filter is applied |
| Pagination | **Cursor-based** for records (`11` §6); offset only for page-numbered reports |
| Counts | Exact for small result sets; the UI shows "approximate" when a counted total is skipped for cost |
| Snippets | Highlighted excerpts generated by `ts_headline`, escaped before render |
| Empty query with filters | Supported; equivalent to a filtered browse |

### 2.5 Filters

Common filter dimensions across record types: status, priority, assignee, team,
catalog item, requester, created/submitted date range, SLA state, tags.

**Every filter maps to an indexed column or is rejected.** An unindexed filter is a
full-table scan wearing a feature's clothes. Filters that cannot be served by an index
are either given one (`09`) or not shipped.

### 2.6 Threshold for an external index

Adopt an external index only if **all** hold, with measurements attached:
- p95 search latency exceeds the target in `02` under production-volume data;
- the query shape requires fuzzy/prefix/typo tolerance PostgreSQL cannot serve;
- a sync pipeline can be maintained with an explicit consistency contract (which
  introduces replication lag into search results).

## 3. Reporting

### 3.1 Classes

| Class | Latency tolerance | Example | Path |
|---|---|---|---|
| Operational dashboard | Seconds | Open requests by priority | Cached aggregate, short TTL |
| Team list reports | Seconds | My team's SLA state | Live indexed query |
| Period analysis | Minutes | Attainment last quarter | Async job, cached result, export |
| Ad hoc export | Minutes | Full record export with filters | Async job → download link |

### 3.2 Correctness rules

| # | Rule | Reason |
|---|---|---|
| R1 | Attainment and duration metrics are recomputed from **stored timestamps**, never from current configuration (`25` §9) | Prevents retroactive rewriting of history |
| R2 | A report states the period boundaries, the time zone, and the scope it was run under | A number without its scope is not a report |
| R3 | Reports are **scoped by the caller's authorization**; there is no "run as admin" report path for an unprivileged caller | Otherwise reporting becomes the authorization bypass |
| R4 | Large reports run as async jobs and produce a download with an expiry | Never block a request thread on an aggregate over the whole table |
| R5 | Exports include the filter used and the generation timestamp; they are audited | Exfiltration accountability |
| R6 | Aggregates over closed periods are immutable for that period once generated | Stable numbers; a changing historical figure is a bug |

### 3.3 Metrics catalogue

| Metric | Owner | Definition |
|---|---|---|
| Requests by status/priority | `22` | Counts, current |
| Mean / median time to resolve | `22` | From `submittedAt` to `resolvedAt`, working time per `25` |
| SLA attainment / breach rate | `25` | Per §9 of `25` |
| Incident volume, MTTR, major-incident count | `23` | Reopen-aware |
| Task completion, overdue count | `24` | |
| Approval turnaround, approval backlog | `26` | Time from instance to decision |
| KB deflection and reopen rate | `27` | Per §6 of `27` |
| Asset utilisation, warranty exposure | `28` | Per `28` |
| Notification delivery/failure rate | `29` | Provider-grade |
| Access denials, override rate | `31` | Security signal |

Each metric names its owner so a wrong metric has exactly one place to be fixed.

### 3.4 Aggregation strategy

```
Live query        small scope, indexed       up to ~10^5 rows for aggregates
Materialised      period aggregates          refreshed by scheduled job (single leader)
Cache             dashboard aggregates       short TTL, invalidated on write of that class
Async job         ad hoc / large export      queued, result stored as a file (19)
```

**Never compute a dashboard by loading all rows and aggregating in the application.**
The database aggregates; the application shapes.

## 4. Permissions

| Action | Permission |
|---|---|
| Search | Same read entitlement as the underlying records |
| Export records | `report:export`, plus record-level visibility |
| View dashboards | `report:read` (scoped to team where applicable) |
| Configure report schedules | `report:manage` |
| Cross-team reporting | `report:read.all` (lead/admin) |

| Method | Path | Notes |
|---|---|---|

| Surface | Contents |
|---|---|
| Global search | Unified results grouped by type, with filters and "why this matched" snippets |
| Saved filters | Persisted per user, shareable within a team |

## 7. Performance Rules

- Cursor pagination on all record listings (`11` §6).
- Statement timeout on every query (`33`); a report that exceeds it is moved to async.
- `EXPLAIN` review is required for any query touching a large table in a new feature
  (`38`, `09`).
- Total counts on large tables are opt-in and clearly labelled approximate.
- N+1 patterns are prohibited; includes are explicit (`13`).

## 8. Edge Cases

| Case | Behaviour |
|---|---|
| Caller searches for a record they cannot see | Not present, in results, counts, or suggestions — no distinction from "does not exist" |
| Same term matches a public and a restricted article | Only the permitted one appears |
| Report period spans a calendar change | Stored target instants are used; numbers do not move (`25` §4) |
| Export exceeds size limit | Truncated with an explicit notice, or split into parts; never silently partial |
| Search index stale after write | PostgreSQL FTS is transactional with the write, so no staleness for this source |
| Download link expires | Regeneration available; expiry is stated at creation |
| Filter on an unindexed field | Not offered; if requested, an index decision is made first |

## 9. Acceptance Criteria

1. Search never returns a record the caller cannot read — verified by a test with a
   restricted record under a broad query, including counts and suggestions.
2. The order is filter → rank → paginate in one query, verified by query inspection.
3. Pagination is cursor-based for record listings and stable under concurrent writes.
4. Reports over closed periods return identical figures across repeated runs.
5. A large export runs asynchronously and returns a time-limited download.
6. Every export is audited with its filters and the requesting user.
7. SLAs in reports are reproduced from stored timestamps, unaffected by later edits to
   policies or calendars.
