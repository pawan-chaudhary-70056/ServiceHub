# Migrations

Migration files land in this directory, generated by Prisma (`npm run prisma:migrate`).

**Rules (docs/10-MIGRATIONS-AND-SEEDING.md and docs/35 §5):**

1. **Never edit a migration that has been deployed.** Add a new one. Migrations are an
   applied, ordered history; rewriting one makes environments diverge silently.
2. **Migrations must be backward compatible with the currently running version.**
   During a rolling deploy both the old and new app versions run against one schema —
   this is why the strategy is *expand → migrate → contract*:
   - expand: add the new column/table, nullable or defaulted;
   - migrate: backfill and switch reads/writes;
   - contract: drop the old column in a **later** release, after the old version is
     retired.
3. **A migration that locks a large table needs `CONCURRENTLY`** for index creation, or
   a batched backfill.
4. **A migration failure aborts the deploy**; the previous version keeps serving.
5. **Seed data is idempotent and synthetic** — no real personal data in any
   non-production environment (docs/37 §3, docs/19).

Index design is owned by `docs/09-DATA-INTEGRITY-AND-INDEXING.md`; every index must be
justified by a query pattern, because indexes cost storage and write maintenance.
